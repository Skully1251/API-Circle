API Circle — High-Level Design (HLD)

Architectural blueprint for a centralized API management and distribution platform. Built on the PERN stack (PostgreSQL, Express, React, Node.js) with NGINX edge routing, a dedicated Node.js application gateway, dual messaging with Kafka & RabbitMQ, and Redis caching.

1. Executive Summary & Problem Statement

Modern digital businesses consume dozens of external APIs while simultaneously seeking to monetize their own digital capabilities. However, integrating directly with fragmented providers introduces severe operational overhead: scattered billing agreements, uncoordinated rate limits, disparate credential formats, and lack of unified security audits.

API Circle acts as an intelligent intermediary and marketplace between API Providers and API Consumers. Built using the PERN stack (PostgreSQL, Express.js, React, Node.js), the platform delivers:

Centralized Marketplace React UI + REST

Self-service portal where consumers discover APIs, inspect interactive documentation, create applications, subscribe to tiered plans, and issue API credentials.

Dual Gateway Architecture NGINX + Node Gateway

NGINX handles edge TLS, basic rate limiting, and HTTP load balancing, forwarding traffic to our internal Express API Gateway for token auth, subscription checks, and proxying.

Resilient Event Fabric Kafka + RabbitMQ

Kafka powers massive asynchronous usage stream analytics, while RabbitMQ coordinates resilient inter-service RPC verification, tasks, and notifications.

2. Primary Actors & Core Use Cases

API Provider

  • Registers organization and provider profile.
  • Publishes APIs with versions, endpoints, and OpenAPI specs.
  • Configures backend upstream URLs & authentication secrets.
  • Defines subscription tiers (Free, Pro, Enterprise) and pricing.
  • Monitors consumer adoption, request volumes, and earnings.

API Consumer

  • Discovers and searches published APIs by category.
  • Creates consumer applications (e.g., Development, Production).
  • Subscribes applications to API plans.
  • Generates, rotates, and revokes dual-hashed API credentials.
  • Consumes third-party APIs through API Circle's unified gateway.

Platform Administrator

  • Manages organizations, users, and marketplace moderation.
  • Monitors platform-wide traffic, error rates, and node health.
  • Enforces platform-wide security policies and WAF directives.
  • Audits billing settlements and provider payout reconciliation.

3. Architecture & Two-Tier Gateway Layering

API Circle implements a distinct Two-Tier Gateway Architecture to cleanly separate edge infrastructure concerns from application-level API management business logic:

Tier 1: Edge NGINX Proxy Edge Traffic Control

NGINX operates as the internet-facing reverse proxy (Ports 80 & 443). Responsibilities include:

  • TLS/SSL Termination: Offloads cryptographic computation from Node.js runtime.
  • Coarse Rate Limiting: limit_req_zone to deflect L7 HTTP flood DDoS attacks before hitting Node.js.
  • High-Speed Load Balancing: Distributes incoming traffic across stateless api-gateway container replicas.
  • Security Headers & Buffering: HSTS, body size enforcement, client connection reuse (HTTP 1.1 keep-alive).
Tier 2: Application API Gateway Node.js / Express

Our dedicated Express-based API Gateway service executes all business-specific API mediation tasks:

  • Credential Authentication: Extracts API key, verifies SHA-256 hash in Redis cache.
  • Subscription & Entitlement Validation: Verifies consumer subscription state and API product bindings.
  • Distributed Rate Limiting: Executes atomic Redis Token Bucket Lua script.
  • Quota Enforcement: Validates monthly consumed call limits.
  • Provider Proxying: Injects provider authentication secrets and streams responses.
  • Asynchronous Telemetry: Emits invocation logs to Kafka.

5. Microservices Decomposition & Service Ownership

API Circle adheres to the Database-per-Service pattern. Services never share database connections or execute cross-schema JOINs. Instead, they interact via clean REST APIs and asynchronous message queues.

6. Database & Redis Caching Strategy

PostgreSQL: Single Source of Truth

All durable platform state resides in a single PostgreSQL 16 cluster, partitioned into isolated logical schemas:

  • auth.*: Credentials, password hashes, roles, permissions, refresh tokens.
  • users.*: Extended profiles, organizations, members, account settings.
  • catalog.*: APIs, categories, versions, endpoints, documentation, provider auth.
  • subscriptions.*: Plans, active consumer subscriptions, usage quota periods.
  • api_keys.*: SHA-256 hashed API keys, key prefix index, usage logs.
  • notifications.*: Templates, delivery attempts, user preferences.

Cross-service entity linkages use standard UUIDv4 identifiers without cross-schema foreign keys, ensuring microservices can migrate to independent physical databases seamlessly as traffic scales.

Redis: High-Performance Hot Cache

The Data Plane (API Gateway) avoids querying PostgreSQL on active request paths. Redis provides sub-millisecond lookups via prefixed namespaces:

  • apikey:hash:<sha256>: Cached key metadata, status, plan ID, rate limits (TTL: 300s).
  • catalog:route:<slug>:<ver>: Upstream provider base URL and auth configs (TTL: 600s).
  • ratelimit:tb:<subId>: Atomic Token Bucket state (tokens count + timestamp).
  • sub:quota:<subId>:<YYYY-MM>: Monthly call counter for quota enforcement.
  • auth:blacklist:<tokenHash>: Revoked JWT / refresh token blacklist.

7. Dual Messaging Architecture: Kafka vs. RabbitMQ

Rather than forcing a single messaging tool to handle incompatible workloads, API Circle employs a Dual Messaging Strategy leveraging the distinct strengths of both Apache Kafka and RabbitMQ:

Messaging System Primary Use Case in API Circle Communication Pattern Why This Broker?
Apache Kafka Data Plane telemetry, raw API usage metering, high-volume analytics ingestion Partitioned Pub/Sub streaming append-log High Ingestion Throughput: The Gateway emits an event for every single API invocation (thousands of events/sec). Kafka handles high-concurrency writes with sequential disk append and supports independent replayable consumer groups without impacting gateway latency.
RabbitMQ Inter-service RPC validation, task queues, transactional email and alert dispatching Direct/Topic Exchange with RPC Request-Reply (Correlation IDs) Flexible Task Routing & Immediate Acknowledgment: Ideal for request-reply workflows (e.g., user-service verifying API key validity via api-key-service over api-key.validate) and durable worker task queues with dead-letter exchanges (DLX) for failed email retries.

9. Security Architecture

1. Dual-Token API Key Pattern

To eliminate database exposure while retaining administrative indexability, credentials follow a dual-token structure:

ac_live_8f3d1b2a_984f10a8b9e6712c40...
  • Public Prefix (ac_live_8f3d1b2a): Stored plaintext for administrative search and UI display.
  • Secret Hash: Computed via SHA-256. Plaintext keys are presented exactly once upon creation and NEVER persisted.
  • Instant Revocation: Revoking a key writes a tombstone into Redis with immediate TTL eviction.

2. Secure Provider Credential Storage

Provider backends often require private API keys, Basic Auth, or OAuth bearer tokens. These credentials are protected via:

  • AES-256-GCM Encryption: Encrypted at rest in catalog.provider_endpoints with 128-bit authentication tags.
  • Master Key Management: Secret keys provided via Docker/Kubernetes environment secrets.
  • SSRF Prevention: Gateway validates provider target URLs against strict protocol (HTTPS only) and hostname allow-lists.

10. Containerization & CI/CD Pipeline (GitHub Actions & GitLab CI)

Docker Orchestration Containerized

Each microservice is packaged as an optimized multi-stage Node.js Alpine container (node:22-alpine). docker-compose.yaml orchestrates local development and multi-container staging:

  • Isolated bridge network: api-network.
  • Explicit health checks for PostgreSQL, Redis, RabbitMQ, and Kafka.
  • Stateless microservices restart automatically on failure.
CI / CD Automation GitHub Actions & GitLab CI

Automated pipelines trigger on pull requests and branch merges across both GitHub Actions and GitLab CI:

  • Stage 1 (Lint & Test): Runs ESLint, Unit tests, and database migration checks using service containers.
  • Stage 2 (Security Scan): Executes npm audit and container vulnerability scanning (Trivy).
  • Stage 3 (Build & Push): Builds multi-arch Docker images, tagging with Git SHA and pushing to Container Registry.
  • Stage 4 (Deploy): Rolling update to staging and production Kubernetes/Docker Swarm clusters.
